从登录到鉴权：理解 JWT、访问令牌与刷新令牌

JWT 如何携带身份信息，又如何通过签名建立信任？本文从登录流程出发，介绍 JWT 的结构、HS256 与 RS256 的区别、后端验证流程，以及访问令牌、刷新令牌和服务端会话的协作方式，厘清签名、加密、认证与鉴权之间的边界。

JWT / 鉴权与授权 / Token / Web 安全 / 后端开发

登录是一次交换：你交出一份凭据（邮箱和密码），服务端确认之后，给你一件能带在身上的东西。HTTP 天生不记事，每一次请求都是初见的陌生人——访问令牌就是那件随身带着的凭据。而在它之前，先要把「你是谁」写进一张纸条，再给这张纸条盖上章，这就是 JWT。

注意：签名不是加密。JWT 的负载只是 Base64URL 编码，复制出来谁都能读——签名保证的是「没被改过」，不是「没人看见」。密码、手机号这类不能公开的东西，不要放进令牌。

为什么需要 JWT？

最朴素的办法是服务端会话：存一张表，每次请求拿着 cookie 来查。一台机器时它简单好用；机器多了，每台都要看得见那张表，于是引入共享存储——会话从「内存里的一小块」变成「另一个必须一直活着的组件」。JWT 换了个方向：状态还给客户端，服务端只验签名，不查表。

POST /auth/login    邮箱 + 密码
  → 200 { accessToken, refreshToken }
后续请求            Authorization: Bearer <accessToken>
  → 验签名 → 通过

在线体验（新窗口）

QA-Agent 是实验室里的一位值班同事：流程怎么走、资料在哪一页、这张图里写的是什么——从前要挨个问人，现在先问它。

它答什么

实验室的问题大致三种来路，它各有一套去处：

  • 流程——按 SOP 答。下一步做什么、材料交给谁，出处指回对应的流程文档；
  • 资料——先检索知识库，再回答。文档改过，答案跟着改，引到的段落摆出来；
  • 图——拍一张设备面板、试剂标签或报错截图，它先读出图里的字和结构，再接着答。

为什么先检索再回答

实验室里，一句凭印象说出来的答案比「不知道」危险得多。所以检索排在生成前面：先去 SOP 和知识库里找到那几段原文，照着回答，并给出处。找不到就不答，不猜。
