登录是一次交换：你交出一份凭据（邮箱和密码），服务端确认之后，给你一件能带在身上的东西。HTTP 天生不记事，每一次请求都是初见的陌生人——访问令牌就是那件随身带着的凭据。而在它之前，先要把「你是谁」写进一张纸条，再给这张纸条盖上章，这就是 JWT。

注意：签名不是加密。JWT 的负载只是 Base64URL 编码，复制出来谁都能读——签名保证的是「没被改过」，不是「没人看见」。密码、手机号这类不能公开的东西，不要放进令牌。

为什么需要 JWT？

最朴素的办法是服务端会话：存一张表，每次请求拿着 cookie 来查。一台机器时它简单好用；机器多了，每台都要看得见那张表，于是引入共享存储——会话从「内存里的一小块」变成「另一个必须一直活着的组件」。JWT 换了个方向：状态还给客户端，服务端只验签名，不查表。

POST /auth/login    邮箱 + 密码
  → 200 { accessToken, refreshToken }
后续请求            Authorization: Bearer <accessToken>
  → 验签名 → 通过

一张 JWT 长什么样

三段：头部、负载、签名，用点连起来。头部说用了哪种签名算法，负载放你要携带的事实——谁、什么时候过期，签名是前两段加上一把只有服务端知道的钥匙算出来的。前两段谁都能读，唯独签名伪造不了：改一个字符，验签就过不去。

HS256 还是 RS256

对称算法只有一把钥匙，签和验用同一把。单服务时它够用；一旦有别的服务也要验签，就得把这把钥匙复制出去——能签名的钥匙落到别人手里，等于谁都能冒充你。所以跨服务时换 RS256：私钥签、公钥验，公钥公开也无妨。

访问令牌与刷新令牌

访问令牌短命，几十分钟就过期，偷去也只能用一个窗口。过期之后不想让人重新输密码，于是有了刷新令牌：它活得久，只在换新访问令牌时用一次。两者的保管方式也不同——访问令牌可以放在内存里，刷新令牌要放在更稳、也更难被脚本读到的地方。

服务端还留着什么

状态并没有完全消失，只是换了位置。要能「让他立刻下线」，服务端还是得记一笔：哪些刷新令牌有效、哪一批已经作废。把这笔账记小、记少，才是 JWT 真正省下来的东西。

把这几件事分开看，边界就清楚了：签名负责完整，过期负责时间，刷新负责续命，服务端那本小账负责反悔。
